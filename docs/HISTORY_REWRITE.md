2026-10-25，经仓库所有者明确确认，`main` 修正了一条历史提交的作者和提交者身份。
其后代的 parent 随之变化：共 49 个提交 SHA 改变，76 个提交原样保留。作者归属改写节点为
`d451a5c12f60764ec7e765a57d56c439dd1b51b0`，对应旧主线

逐提交校验表明，归属改写本身没有改变任何 tree、提交消息、日期或时区；其他作者、原签名对象和合并拓扑保留。
没有修改金额、支付、幂等、安全协议、数据库迁移、历史业务快照或任何生产程序。
[完整旧新 SHA 对照](history-author-map.json)仅用于追溯，**不是安装授权、发行来源凭据或放宽校验的白名单**。

远程和本地只保留 `main` 分支。旧标签、Release、版本号与附件身份及摘要不变；因此旧标签仍能访问原历史，
不是全仓历史抹除。旧提交的 CI、截图和验收记录仍只证明其原 SHA，不能直接作为新 SHA 的绿灯。
新主线须重新运行自己的检查；本公告不预先宣称它们已经通过。

## 旧版新安装与升级暂存受阻

**旧 Core v0.5.6、v0.5.7、v0.5.8、v0.5.9 的新 `prepare` / `stage` 当前受阻。**
这些发行版仍可下载，资产未变；但主机来源验证要求资产源码、构建来源和 provenance 的信任点保留在当前 `main` 的祖先链。
改写后的主线与上述旧标签分叉，原安装/升级工具会按既有安全规则拒绝。换用旧包内工具或本地资产目录不能绕过这一来源门槛。

这不是停止现有服务的操作。已经真实准备、仍受保护的旧目录，其本地收据、文件摘要和 schema 兼容条件仍须独立核验；
不能因此伪造新收据、跳过来源检查、复用不匹配程序/数据库或删除 journal。
2026-10-27，新主线Core **0.5.10**已完成正常Release `424987299`、正式构建/独立发布器及Ubuntu22/24公开六资产/生产prepare复验，精确source为`dab0167`，见[公开验收](CORE_PUBLIC_PREPARE_ACCEPTANCE.md)。这重新建立新版本来源链，不使旧0.5.6–0.5.9的新prepare恢复可用，也不替代已有旧目录或目标主机升级验收。不移动旧标签、不替换历史资产、不弱化生产校验。

1. 当前 `main` 内新的 Core 0.5.10 版本、前端包版本、插件管理器默认版本一致；SMTP 保持独立 1.1.0。资源协议首次发行最低 Core 明确为 0.5.10，不再把旧 0.5.9 误标为支持。
2. 先通过精确候选提交的完整 CI，再新建未占用标签，由正式构建/独立发布器产生新六资产。旧历史不合并回来，也不为旧 SHA 添加信任白名单。
3. 新 target 的源码及 provenance 策略点必须是当前 main 祖先，沿用全部既有源码/资产/构建校验；`update-manager.py` 的生产祖先条件没有改动。
4. 已有实例若保留原路径的真实 `PREPARED.json` 和完整受保护旧目录，可用新工具做本地收据/文件/BUILD/迁移前缀核查，再审查更高版本的升级计划。新目标独立通过官方来源校验；这不是让分叉旧 tag 重新通过网络验证。
5. 缺收据、文件被改、迁移不一致等情形继续拒绝，不能伪造旧收据、补签新身份或只改版本号。schema 仍为 13，没有新增迁移；升级停写、备份恢复验证、秘密与服务检查不省略。

2026-10-25初始回归使用合成官方响应/ELF与真实prepare生成的本地目录收据，服务及数据库为离线fixture；当时只验证代码路径，不能说明公开资产或客户环境。后续22/24完整native与新公开prepare已分别通过；Darwin不支持的Linux原子操作未被放宽。仍不承诺任意旧分叉目录已完成真实升级，详见[0.5.10版本合同](../vps-billing/docs/RELEASE-v0.5.10.md)和[升级步骤](../vps-billing/docs/UPGRADE.md)。

## 已有克隆与备份

已有开发克隆应先保存自己的未提交修改和未推送提交，再获取新 `main`；不要把旧主线重新合并进新主线，
否则会重新引入已修正的作者历史。不要对有本地修改的工作区直接执行硬重置。
仓库维护端在操作前保存了完整 Git bundle 和逐提交旧新映射；需要恢复时先核对精确旧新 SHA，
不对远程使用无租约的强推，不批量推送旧标签或内部应用引用。

GitHub 的贡献者显示可能缓存旧统计；主线作者集合与网页刷新是两个独立核对项。
