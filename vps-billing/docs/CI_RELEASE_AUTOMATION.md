# CI 与正常 Release 自动化

工作流只为 `xiaoqiqixi/betteridcsys` 验证精确源码并交付 Core/独立 SMTP 程序包。只读检查、只读构建、受信发布分开；没有用户服务器、Mac、真实付款或外部发信步骤。正式 Release 的最终状态为公开、非草稿、非预发布，不能据此宣称商业运营条件或主控/被控已完成。

## 权限与流程

| 工作流                | 入口                                                               | 权限和产物                                                                                  |
| --------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `ci.yml`              | `main` push / 手动                                                 | 只读源码；应用、数据库、原生、浏览器与安全检查，不发布                                      |
| `release-build.yml`   | Core `vX.Y.Z` 或 SMTP `smtp-vX.Y.Z` 标签；默认分支手动指定已有标签 | 只读；验证精确标签源码，按包种类构建两次并比对，生成来源记录与 Actions artifact             |
| `release-publish.yml` | 指定构建流程成功结束                                               | 仅发布 job 有 `contents: write` / `actions: read`；默认分支受信程序核验后上传并公开 Release |

`workflow_run` 是单独的写权限边界。发布 job 不执行上游源码或下载包的脚本、Python 模块、二进制；仅执行默认分支控制程序。下载内容作为有上限的待核验数据处理，不覆盖受信控制文件。

## 来源与标签守卫

入口按完整、首尾锚定的稳定语义版本验证标签；普通分支名、任意 SHA、路径片段、空白与额外后缀均不能作为发布标签。标签解析结果须与 `source_commit` 相同，并属于 `main` 历史；Core 和 SMTP 包种类由标签明确确定，版本不得与源码声明不符。

发布器从 GitHub 核对仓库身份、默认分支、触发 run 的 workflow/事件/状态/head、run attempt 与目标 artifact，不能只相信下载的 JSON 声明。构建、打包与发布控制文件的 Git blob 必须与受信默认分支版本一致；旧控制程序或修改过的配方不能借历史成功记录取得写权限。

不创建、移动或删除标签，不覆盖历史 Release 或资产。重复标签或已有同名 Release 使流程停止。外部写入者在校验后仍可改变标签/Release；工作流检查不是跨 API 原子锁，也不是针对恶意仓库写权限的通用沙箱。进一步保护需要仓库规则，流程不自动改权限或规则。

## 构建检查

工具链与锁文件绑定所选源码，当前基线 Go `1.27.3`、Node.js `24.19.0`，实际 npm 与扫描版本由来源及 job 日志记录。Core/SMTP 标签入口都先执行要求的源码验证：

- Go race/vet、真实 `_test` MySQL、前端测试/类型/格式/生产构建、HTTP/config 与发布负向测试。
- 两套独立的一次性 Ubuntu22.04/24.04 runner 上的真实 systemd/Nginx、localhost 私有测试 CA HTTPS、运行/迁移身份分离、API 重启，以及包含支付尝试和结算记录的备份与空库恢复检查。两平台结果分别记录，不相互代替。
- Core 执行器实际创建专用实例、初始化、配置和激活；以独立核验的正式 0.5.2 为升级起点，验证新源码构建候选的升级、重复操作、故障恢复及 schema 不兼容时保留维护状态。候选包在发布前明确标记为源码构建，不伪造官方准备回执或 Actions 来源；正式来源读取走固定官方校验路径。具体已执行场景只认对应 run 的 `CORE_NATIVE_*_JSON` 及验证记录。
- 运行时插件：根目录/策略/程序哈希、握手/身份/大小/错误/时限守卫；独立 UID 的实际安装/替换/回退与故障恢复，Core 程序哈希/PID 和业务继续响应证据。支付另验证原始合成通知 HMAC、金额与币种绑定、幂等结算、交易唯一性及取消互斥。
- 开启沙箱的云端 Chrome，合成订单的桌面/手机回归。不可用则失败，不关闭浏览器安全策略。
- npm、独立 Go 漏洞扫描及固定 actionlint 工作流检查。网络失败不跳过；报告可达函数、导入包和模块级告警各自范围。

真实数据库夹具分别使用固定官方 MySQL8.4.11 Noble / 8.4.13 Jammy 包大小与SHA256，先全部验证再提取；不运行包维护脚本、不接管用户实例。MySQL固定来源清单通过官方HTTPS元数据建立，不能描述为本地InRelease签名验证。
Jammy的Nginx另使用经过官方签名metadata审查的固定stable1.30.6包，避免发行版1.18缺少安全SNI拒绝；Noble仍为认证APT包。不会向主机添加新仓库或签名信任，详见[W04合同](../../docs/FINANCE_NATIVE_22_24.md)。

Chrome 执行前验证预装包记录和文件权限；一次性 runner 中只收紧登记的 root 所有目录和 Chrome 文件树，不替换二进制、不改变内核/AppArmor/沙箱设置。该记录比对不是独立外部来源签名。测试资源、临时 CA/身份/服务和回环进程必须留存清理结果。

应用常规 CI 与原生/浏览器/扫描各自结果都以实际 run 为准；历史结果不沿用到新改动。具体执行记录集中在 [VALIDATION.md](VALIDATION.md)。

## 资产与公开发布

新分发的 artifact 为 Core 六资产或 SMTP 五资产：对应原始 Linux amd64 ELF、单独资源包、`BUILD.json`、`PROVENANCE.json` 与 `SHA256SUMS`，精确文件名见 [发布清单](RELEASE.md)。BUILD schema 3 / `raw-binaries-v1` 绑定逻辑程序与原始文件；资源包不含 ELF。旧四资产归档读取路径兼容保留，已公开文件不改写。不手动上传源码包；GitHub 自带源码附件不由该程序产生。Core 的两个原始程序与网页/迁移/部署资源共同组成安装；SMTP 的原始程序与五文件资源经核验组装。文件集合按包种类严格校验，拒绝多余/重复/穿越路径、链接、超限内容、错误摘要和不匹配来源。

两次构建比对完整输出；来源记录绑定精确 commit、标签、run/attempt、控制文件、大小与 SHA-256。发布器验证完所有资产才公开：暂存阶段 `draft=true`，全部上传并核实后执行限定的状态修改，最终 `draft=false`、`prerelease=false`。Core 可以更新 latest，SMTP 不能抢占 Core latest。任何最终状态或资产复查失败都需报告真实失败/不确定状态，不把中间 artifact 或草稿视为发布成功。

来源记录没有签名，不是 SLSA 认证或完整 SPDX/CycloneDX SBOM。SHA 只验证与清单一致，仍需确认仓库与下载渠道。常规发布不删除旧附件。旧 Release／草稿的单独授权清理不由发布流水线执行；保留当前 Core／SMTP、全部 Git 标签和源码历史，不扩大发布 job 权限来完成清理。

## 结果和部署边界

只读 CI、成功构建、正常 Release、真实安装是独立事实。公开发布不部署服务器，文档命令也不会自动在用户主机执行。CI 不验证宝塔面板组合、真实域名/公共 CA 签发续期、数据库进程或整机恢复、跨 schema 降级、独立实例/异地灾备、容量、外部 SMTP 投递或真实服务商支付结算。运营放行需按 [RELEASE.md](RELEASE.md) 和实际环境另行判断。

检查失败先保留精确 action/run/资产状态。已执行操作先核对结果，禁止移动标签、重建旧包或削弱守卫以取得绿灯。API 拒绝操作时记录明确原因和真实状态，不绕过仓库权限或发布守卫。
